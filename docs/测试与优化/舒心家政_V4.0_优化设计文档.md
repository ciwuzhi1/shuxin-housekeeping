# 舒心家政 · 系统优化设计文档

> 文档版本：V4.0  
> 基线版本：v3.5  
> 基线日期：2026-08-14  
> 项目形态：React + Vite + FastAPI + MySQL  
> 文档目标：在保持当前项目真实可运行、轻量部署和 GitHub 开源友好的前提下，系统解决架构可维护性、测试完整性、安全性、性能、数据一致性和生产化能力问题。

---

## 1. 文档目标

当前项目已经从 Express + SQLite 迁移为 FastAPI + MySQL，具备真实后端、JWT 鉴权、角色 + 资源归属双重校验、订单状态机、财务流水、评价落库以及自动化 pytest 回归能力。

现阶段的优化重点不再是“补基础功能”，而是：

1. 保持当前本地部署简单，不引入 Redis、Kafka、RabbitMQ、Celery、向量数据库等重型组件。
2. 将路由中的 SQL 与业务逻辑逐步抽离，降低维护成本。
3. 建立数据库迁移机制，彻底解决“删库重建 schema”的问题。
4. 将密码安全从 SHA-256 + 固定盐升级为生产级慢哈希。
5. 加强 JWT、CORS、限流、输入校验、敏感字段脱敏。
6. 建立完整的单元测试、集成测试、API 安全测试、前端测试和基础压测体系。
7. 将静态展示数据与真实统计接口逐步分离。
8. 在不改变当前用户体验的情况下，为未来容器化和云部署保留扩展空间。

# 3. 优化原则

## 3.1 轻量优先

本阶段不强制加入：

- Redis
- Kafka
- RabbitMQ
- Celery
- Elasticsearch
- 向量数据库
- Kubernetes

原因不是这些技术没有价值，而是当前系统业务规模不足以证明其必要性。

优先使用：

- FastAPI
- MySQL
- Pydantic
- PyMySQL
- pytest
- Alembic
- Vitest
- Testing Library
- Locust（仅测试环境）

这样可以保持“一台普通电脑即可完整运行”的特点。

## 3.2 安全优先

所有来自浏览器的：

- userId
- role
- amount
- price
- providerId
- status

都不能作为最终可信依据。

后端必须以：

> JWT 身份 + 数据库真实状态 + 服务端业务规则

作为最终判断来源。

## 3.3 渐进式重构

不一次性重写现有项目。

推荐顺序：

`Router → Service → Repository → Database`

先拆订单，再拆财务、用户、评价，最后逐步收敛。

## 4.2 Router 层职责

Router 只负责：

1. 接收 HTTP 请求。
2. 解析 Pydantic Schema。
3. 获取当前用户。
4. 调用 Service。
5. 返回统一响应。

禁止在 Router 中持续增加复杂 SQL 和核心业务规则。

示例：

```python
@router.post("/{order_id}/status")
def update_status(
    order_id: str,
    payload: OrderStatusUpdate,
    current_user=Depends(require_auth)
):
    result = order_service.update_status(
        order_id=order_id,
        user=current_user,
        target_status=payload.status
    )
    return success(result)
```

# 6. Repository 层设计

Repository 只负责数据库访问。

```python
class OrderRepository:

    def get_by_id(self, order_id):
        ...

    def update_status(self, order_id, status):
        ...

    def create(self, data):
        ...

    def list_by_client(self, client_id):
        ...

    def list_by_provider(self, provider_id):
        ...
```

禁止 Repository 判断：

- 用户有没有权限
- 当前状态能不能转换
- 是否应该退款

这些逻辑必须留在 Service。

# 7. 数据库迁移优化

## 7.1 当前问题

当前 schema 变更主要依赖：

```text
DROP DATABASE
CREATE DATABASE
重新执行 schema.sql
```

这种方式适合演示项目，不适合：

- 多人协作
- GitHub 开源
- 测试环境
- 生产环境
- 数据保留

## 7.2 推荐方案

引入 Alembic。

迁移流程：

```bash
alembic revision --autogenerate -m "add order index"
alembic upgrade head
```

开发环境可以继续保留：

```bash
python scripts/reset_db.py
```

但是生产环境禁止用删库重建作为迁移方式。

## 7.3 Migration 规则

每次数据库结构修改必须：

1. 创建 migration。
2. 编写 rollback。
3. 更新 schema 文档。
4. 增加对应测试。
5. 检查旧数据兼容性。

# 8. 密码安全优化

当前：

```text
SHA-256 + 固定盐
```

属于演示级安全方案。

生产建议升级：

```text
Argon2id
```

或：

```text
bcrypt
```

推荐优先 Argon2id。

## 8.1 迁移策略

不要一次性清空历史密码。

支持：

```text
旧密码 SHA-256
        ↓ 登录成功
重新计算 Argon2id
        ↓
覆盖 password_hash
```

最终达到：

```text
新用户 → Argon2id
旧用户 → 首次成功登录后自动升级
```

# 9. JWT 安全优化

当前 JWT 主要问题：

- 开发环境存在默认 JWT_SECRET。
- 生命周期固定。
- 缺少 refresh token 体系。

优化：

```text
Access Token：15~30 分钟
Refresh Token：7~30 天
```

生产配置：

```env
JWT_SECRET=<strong-random-secret>
JWT_EXPIRES=1800
REFRESH_TOKEN_EXPIRES=2592000
```

同时增加：

- token 签发时间
- token 唯一 ID
- token 类型
- issuer
- audience

# 11. 接口安全规则

## 11.1 用户 ID

错误：

```http
GET /api/orders?clientId=c2
```

后端直接相信 clientId。

正确方式：

```text
JWT userId = c1
        ↓
后端强制使用 c1
        ↓
忽略客户端传入的 clientId
```

## 11.2 金额

客户端：

```json
{
  "unitPrice": 1,
  "totalHours": 10,
  "totalAmount": 1
}
```

后端重新计算：

```text
catalog_price × total_hours
```

最终金额不接受客户端决定。

## 11.3 角色

客户端传：

```json
{
  "role": "admin"
}
```

不能改变权限。

权限必须来自 JWT + 数据库身份。

# 12. 数据库一致性优化

订单完成必须在一个事务内完成：

```text
BEGIN
  update orders
  update provider balance
  update completed_orders
  insert income
COMMIT
```

失败：

```text
ROLLBACK
```

禁止出现：

```text
订单完成了
但流水没写进去
```

建议为流水增加业务唯一键，例如：

```text
(order_id, transaction_type)
```

防止重复结算。

# 13. 数据库索引优化

重点检查：

```sql
orders(client_id)
orders(provider_id)
orders(status)
orders(created_at)
transactions(provider_id)
transactions(order_id)
reviews(order_id)
reviews(provider_id)
notifications(user_id)
```

组合查询可以增加：

```sql
INDEX idx_orders_provider_status(provider_id, status);
INDEX idx_orders_client_status(client_id, status);
INDEX idx_transactions_provider_created(provider_id, created_at);
```

原则：

> 先通过 EXPLAIN 证明慢查询，再添加索引。

禁止为了“看起来专业”无限增加索引。

# 14. 查询与分页优化

分页统一使用：

```text
page
pageSize
```

并限制：

```text
pageSize <= 100
```

已有 PAGE_SIZE / MAX_PAGE_SIZE 配置继续保留。

大数据量场景进一步考虑游标分页：

```text
created_at + id
```

当前 9 单的演示项目不必提前复杂化。

# 15. 缓存策略

当前项目不建议为了缓存而引入 Redis。

优先：

1. MySQL 索引。
2. SQL 查询优化。
3. 合理分页。
4. 后端进程内短期缓存。

只对：

- categories
- service catalog
- 系统配置

等低频变化数据考虑进程级缓存。

订单、余额、财务流水禁止使用无效缓存。

# 16. Mock 降级策略优化

当前：

```text
API 失败 → Mock
```

优点：

- 演示稳定。
- 后端未启动时前端仍可展示。

问题：

生产环境可能掩盖后端故障。

建议区分：

```text
Development:
API failure → Mock

Production:
API failure → Error State
```

并在生产环境默认：

```env
ENABLE_MOCK_FALLBACK=false
```

# 19. 并发与幂等

重点防止：

```text
两个家政员同时抢一个订单
```

必须保证最终只能成功一个。

推荐：

```sql
UPDATE orders
SET provider_id = ?,
    status = 'accepted'
WHERE id = ?
  AND status = 'pending'
  AND provider_id IS NULL
```

检查：

```text
affected_rows == 1
```

否则返回：

```text
409 Conflict
```
