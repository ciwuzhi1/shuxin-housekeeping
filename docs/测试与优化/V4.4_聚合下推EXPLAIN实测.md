# V4.4a · 聚合下推 EXPLAIN 实测记录

> 对应优化设计文档第 13 节原则「先通过 EXPLAIN 证明,再添加索引/优化」。
> 实测环境:本机 MySQL 8.0,开发库 housekeeping(种子数据:orders 12 行 / users 8 行),2026-09-04。
> 改动:admin.stats / finance.summary / provider.earnings / provider.stats / client.stats 五处
> 「全表(或按人全量)拉取 → Python 内存统计」改为 SQL 条件聚合单行返回;响应 JSON 逐字段不变。

## 一、改造点与实测对比

| 接口 | 改造前查询(EXPLAIN) | 改造后查询(EXPLAIN) | 变化本质 |
|---|---|---|---|
| GET /api/admin/stats | `SELECT status,total_amount,... FROM orders`(type=ALL,返回 12 行×5列)→ Python 求和;用户侧同样全表 3 次 | `SELECT COUNT(*),SUM(status='completed'),SUM(CASE...) FROM orders`(type=ALL,返回 **1 行×3列**);用户 1 行×4列;MAU 改 COUNT(DISTINCT)(type=range,key=idx_orders_created) | 行数 12→1,传输列 5→3;**DB→应用往返行数 O(n)→O(1)** |
| GET /api/finance/summary | completed 订单全量拉取(ALL,12 行)+ 待退款/待打款全量拉取 → Python 求和 | 3 条标量聚合(1 行 each);分类/月度本已 GROUP BY | 3 次多行传输 → 3 次单行 |
| GET /api/provider/{id}/earnings | 本人 completed 订单全量拉取(ASC)→ Python 求和 + 切片取最近 10 条;recentOrders 曾随全量传输 | `COUNT/SUM` 聚合 1 行 + `ORDER BY created_at DESC LIMIT 10` 只取 10 行 | 数据量增长后传输行数从「全部完成单」降为「≤10」 |
| GET /api/provider/{id}/stats | 本人全部订单拉取 → Python 按 status 计数 | 单行条件聚合 | O(n)→O(1) |
| GET /api/client/{id}/stats | 本人全部订单拉取 → Python 统计 | 单行条件聚合 | O(n)→O(1) |
| GET /api/health | 7 条独立 `SELECT COUNT(*)`(7 次往返) | 1 条子查询(1 次往返) | 往返 7→1 |

## 二、诚实结论

1. **当前演示规模(orders 12 行)下,EXPLAIN 的 type/rows 与改造前几乎相同**(均为全表扫描,优化器对小表选择全扫是正确行为);性能收益体现在**应用侧**——DB→Python 的传输行数从 O(n) 降为 O(1)、Python 循环统计消失、健康检查往返 7→1。真正的查询效率差异要等数据量上来后才会在 EXPLAIN/耗时中显现。
2. `COUNT(DISTINCT client_id)` 场景命中了已有索引 `idx_orders_created`(range);其余聚合走全表扫描在当前规模合理,符合文档「禁止为了看起来专业无限增加索引」原则,**未新增索引**。
3. 后续若 orders 增长到万级,可再评估 `(status, total_amount)` 冗余或汇总表,本期不做。
